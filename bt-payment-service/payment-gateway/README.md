# BharatTruck Payment Service

A production-ready, modular, and highly scalable Payment Service microservice for the **BharatTruck** logistics platform. 

This service is designed as a standalone system using a clean, modern, layered architecture that coordinates payment orders, third-party gateway integrations (Razorpay), secure webhook event handlers, Proof of Delivery (POD) confirmations, and safe escrow releases.

---

## 🚀 Features

- **Payment Orders**: Initiate cargo payment orders with Razorpay, tracking transactions locally from `CREATED` to `INITIATED`.
- **Durable Webhooks**: Process payment success/failure webhooks from Razorpay with automated signature verification.
- **Idempotency Manager**: Track incoming events in the database to prevent duplicate payment processing.
- **Escrow Hold & Release**: Securely hold payments in escrow upon capture. Validate release conditions (captured payment + verified POD) before settling funds.
- **Proof of Delivery (POD)**: Upload cargo pictures and verify them. Enforces that only one POD can be verified for a booking (HTTP 409 Conflict if duplicates are verified).
- **Audit Logging**: Maintain an immutable audit ledger of all critical escrow hold, release, and status transition events.
- **Production-Grade Configs**: Enforce strict fail-fast validation on startup for environmental settings and API keys.
- **Structured Health Probes**: Lightweight endpoint reporting liveness, environment settings, and database viability (HTTP 503 on database disconnection).

## 📐 High-Level Architecture

The service is built on the principles of **Clean Architecture**, separating concerns into layers:

1. **API Layer (`app/api`)**: REST controllers validation and serialization using Pydantic.
2. **Service Layer (`app/services`)**: Business policies and use-case orchestrators raising domain-specific exceptions.
3. **Repository Layer (`app/repositories`)**: Persistence abstraction using SQLAlchemy 2.0 query patterns.
4. **Provider Layer (`app/providers`)**: Gateways integration client interface (Razorpay implementation).

For detailed information on the layer boundaries and dependency mapping, refer to the [Architecture Guide](file:///c:/Users/Agraney/Desktop/payyment/payment-gateway/docs/architecture.md).

## 🔌 API Overview

### System
- `GET /` - Root status and environment details.
- `GET /health` - Lightweight structured system health indicator (returns HTTP 503 on database connectivity errors).

### Payments
- `POST /payments/create-order` - Create a payment order.
- `GET /payments/{payment_id}` - Retrieve payment transaction details.
- `GET /payments/booking/{booking_id}` - Retrieve all payment transactions for a booking.

### Proof of Delivery (POD)
- `POST /pod/upload` - Upload a cargo delivery photo slip.
- `POST /pod/{pod_id}/verify` - Verify a cargo slip (enforces at most one verified POD per booking).
- `POST /pod/{pod_id}/reject` - Reject an uploaded cargo slip.
- `GET /pod/booking/{booking_id}` - Retrieve all uploaded POD events for a booking.

### Escrow
- `GET /escrow/payment/{payment_id}` - Retrieve escrow hold details.
- `POST /escrow/payment/{payment_id}/release` - Release HELD escrow funds (requires a verified POD).

## 🔄 Core Lifecycles

### Payment Lifecycle
```text
  [CREATED] ──► [INITIATED] ──► [CAPTURED] (Escrow holds initialized)
                       │
                       └──► [FAILED]
```

### Escrow Lifecycle
```text
  [HELD] (Triggered on Captured Payment) ──► [RELEASED] (Triggered on Verified POD)
```

### Webhook Lifecycle
```text
  [RECEIVED] ──► [PROCESSING] ──► [PROCESSED] (Durable idempotency check)
                       │
                       └──► [FAILED]
```

## 🚀 Local Installation & Running

### 1. Setup Virtual Environment & Dependencies
```bash
python -m venv .venv
# Activate virtual environment
# Windows (PowerShell):
.venv\Scripts\Activate.ps1
# Linux/macOS:
source .venv/bin/activate

pip install -r requirements.txt
```

### 2. Database Migrations
Deploy/upgrade database schema to PostgreSQL/SQLite using Alembic:
```bash
alembic upgrade head
```

### 3. Start Local Server
Start FastAPI server locally via Uvicorn:
```bash
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```
- **Swagger Documentation**: [http://127.0.0.1:8000/api/v1/docs](http://127.0.0.1:8000/api/v1/docs)
- **Redoc Documentation**: [http://127.0.0.1:8000/api/v1/redoc](http://127.0.0.1:8000/api/v1/redoc)

### 4. Running Tests
Run tests against the Pytest suite (automatically utilizes transactional in-memory SQLite):
```bash
pytest
```

## 🔮 Future Improvements (Roadmap)

To prepare the microservice for high-scale enterprise operations:
- **PostgreSQL Production Cluster**: Transition database infrastructure to a multi-node PostgreSQL cluster with read/write separation.
- **Distributed Caching (Redis)**: Introduce Redis caching for fast payment statuses and session querying.
- **Asynchronous Background Processing**: Integrate Celery or RabbitMQ to manage webhook retries, transaction reconciliation, and notification delivery.
- **Stripe Provider Integration**: Implement a Stripe payment provider class inheriting from `PaymentProvider` to support global card processing.
- **Observability Metrics**: Mount Prometheus exporter middleware and Grafana dashboard hooks to monitor API latency, transaction failure rates, and system CPU/Memory loads.
